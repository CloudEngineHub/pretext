# Development

Commands are in `package.json` and the header of `harness/cli.ts`; the harness and the bench are in [harness/README.md](harness/README.md).

## Setup And Checks

Run `bun install` in a fresh checkout or worktree. `bun test --parallel` runs the unit tests, the harness's offline tests and the doc citation check, and `bun run check` the type check, lint, unused-code check and a check that the generated tables match their sources; both run without a browser. The type check runs twice: over the repository, then over `src/` alone under the settings the package is built with (`tsconfig.build.json`), where an import without its `.js` extension, one ending in `.ts` and a Node or Bun global are errors. The browser harness needs pinned browser copies and webkit-host built first ([harness/README.md](harness/README.md), Setup).

## The Demo Server

`bun start` listens on every network interface, not only localhost, so a phone on the same Wi-Fi can open the demos; a PR binding it to localhost was closed for that (#114). It first kills whatever listens on port 3000, so a server left running from before can't hold the port.

## Engine Data

The break and grapheme tables (`src/generated/engine-break-data.ts`) are refreshed by hand, never in a build step: each must be the copy one browser build ships, and copies drift (Chromium 147's `line_normal.brk` differs from 153's on 239 code points, 2026-09-16). `bun harness repin` says when a browser no longer holds the files of `scripts/engine-data/` that its `sources.json` lists, the engines' compiled rules and ICU's two property sources; then refresh that folder as the header of `scripts/generate-engine-break-data.ts` describes, run `bun run generate:engine-break-data`, then the grapheme check. The script classes in the same module (which scripts a character is in, and the bracket pairs, for Blink's script runs) come from two of ICU's C sources, whose arrays a browser compiles into its binary: `repin chrome` and `repin firefox` look for each array's bytes there, since Firefox's ICU holds the same two files and its profile reads the same classes. `repin` looks for no other file of that folder. The two pair tables (`break_iterator_data_inline_header.h`, which Chromium's build generates, and WebKit's `BreakablePositions.cpp`) have to be read again in the engine's source at each new build, as any fact read in source does (RESEARCH.md, Engine Facts): one that changed shows at a repin only where a recorded case holds the pair (ENGINE_FOLLOWUPS.md, Harness debt). Firefox's `properties.json` isn't looked for either, but the property arrays `repin firefox` finds hold the values it was compared with (the generator's header). The generator checks what it writes by unpacking it with `src/line-breaks.ts`, which imports the generated module, so it runs only while the module on disk loads with every export the library imports. A refresh of the data needs nothing more. A change to the module's exports goes in two steps, the generator's output first, run once, then the library's import; and a module that doesn't load, deleted or left with conflict markers by a merge, is restored from git before the generator runs. On macOS `bun test` also runs the port and the tables against the system's ICU, the one Safari runs, with no browser (`harness/icu.test.ts`): that is what stands in for a byte check of libicucore's two dumps, `locales.json` and `quotation.json`, in the locales the test lists. Safari's generic-family table (`src/generated/webkit-generic-families.ts`: which font each generic family, such as `sans-serif`, names under each page language) comes from Core Text's answers dumped on one macOS and iOS release (`scripts/generate-webkit-generic-families.ts`, run by `bun run generate:webkit-generic-families`, says how they were taken); nothing checks it against a newer macOS or iOS but a new dump.

The engine files stay checked in so the tables rebuild offline, and so does the 30 MB behavior catalog (`harness/cases/catalog.ndjson`): its widths came from bisecting in the browsers, so it can't be made again offline, and deleting it wouldn't shrink the repository, since git history keeps it.

### Grapheme Check

After a grapheme table changes, compare `src/graphemes.ts` with `Intl.Segmenter` in Chrome, Firefox and webkit-host (the harness's background app on the system WebKit that Safari runs); the headers in `scripts/grapheme-check/` have the commands.

## Releasing

The figures a release states are measured on the release commit: none is kept up to date between releases.

1. Run `bun run package-smoke-test`, the only check that packs and imports the built package.
2. Read CHANGELOG.md's Unreleased section as a user of the last release would. Fold an entry that fixes or speeds up something only an unreleased main had into the entry that brought it (as #386 and #419 went into #381's). Check each entry against the last release: by running both builds on a stand-in Canvas; for an entry on types, by compiling against both builds' declarations; for kerning, real fonts and emoji, by the entry's pull request and the old code.
3. State speed once, from a foreground bench against the last release: `bun harness bench <its tag> --foreground --sessions=3` (installed Safari and focused windows, one at a time, where the bench a change runs is side by side in background windows; [harness/README.md](harness/README.md), Bench). Correct the changelog's speed entry from it, the browser versions and the machine it names too. Time Chrome a group of rows at a time (`--browser=chrome --rows=new,seen`, then `rich,resize,lines`, `worst` and `fresh`): in one run of every row against 0.0.9 its processes held 6,232 MB, past the harness's 6,144 MB bound, and its session failed (2026-10-05). The `worst` group alone sits at that bound against 0.0.9: of the three sessions it started on 2026-10-13 two failed, at 6,160 and 6,185 MB, after which the bench starts no further one, and the group's figures are then those of the sessions that completed, one that day, which the bench prints as a hypothesis. The speed entry's milliseconds are read from the fresh-page table, the candidate's medians less base's: loading is its compile and run columns added, the first text its first batch and the text after that its second, a batch's time being its µs a unit times its units (`FRESH_UNITS`, `harness/bench/run.ts`). Its two sentences on rich inline are the rows `rich | chat` and `rich | chat-styled`. The bench has no row for the entry's label figures by language, since it times the labels of 35 languages mixed (`new | labels new`): time each language's labels alone against two copies of the last release (RESEARCH.md, Break Opportunities From Engine Data; the script isn't in the repository), or state the label sentence without figures.
4. Measure the sizes the changelog names: each entry point's bundle (`bun build src/layout.ts --minify`, then `gzip -9`) and the npm package (`npm pack --dry-run`).

Every push to `main` publishes the demo site (`.github/workflows/pages.yml`).

## Deep Profiling

Bun and Node microbenchmarks suit quick experiments; browser behavior needs browser measurements. For an algorithmic change, grow the text and its segments, forced lines and rich items (repeated punctuation, Arabic joins, CJK keep-all, long hyphenated URLs, whitespace runs), and count visited boundaries and submitted Canvas text with cold caches before trusting a timing: doubling an input should not quadruple repeated work ([RESEARCH.md](RESEARCH.md), Keeping Work Bounded).
