# Engine Follow-ups

Open engine work: gaps, deferred decisions, harness debt and actions outside the repo. A deferred decision leaves this file in the same change that records the maintainer's answer, for RESEARCH.md's Decisions Log if the code doesn't show its reason; a gap leaves with the PR that fixes it.

Pick work by demand, not by sweeping this list (RESEARCH.md, Engineering), and work depth-first, finishing a change under way before starting new discovery (RESEARCH.md, Docs). Demand shows in the `Real usage` headings of `harness/accepted/<browser>.txt`, the failures from the harness's real-usage sample, whose draws follow how often apps lay out each kind of text (harness/README.md, Two kinds of set); at b1fd05fc (main on 2026-09-27) the largest were WebKit's soft hyphens, Chrome's Japanese and Chinese lines, and Arabic and Urdu with letter spacing. Most entries below matter only under 24px or in adversarial text.

Terms used below:
- The Chromium (or Blink), WebKit and Gecko profiles are Pretext's rules for Chrome, Safari and Firefox, picked from the user agent (`getEngineProfile()` in `src/measurement.ts`); the scans are their ports of each engine's break-opportunity scan (`src/line-breaks.ts`, `src/gecko-line-breaks.ts`).
- webkit-host is the system WebKit that installed Safari runs, which the harness drives in a background app (harness/README.md, Browsers and pins).
- The stand-in Canvas is the harness's fake measurer (`harness/invariants.ts`, used by `bun harness equal --offline`): it gives characters made-up widths from a formula, not a font's, so a result on it says nothing about shaping.
- Main before #340 is commit 6d1d2106 (2026-09-24), the last main whose break rules were Pretext's own rather than ports of the engines' line breakers.
- The old test suite is `tests/wrapping`, which the harness replaced (#341) and which was removed on 2026-09-25 (#348); its counts stay only where they carry a decision.
- The per-engine rebuild is branch `rebuild-20260916`: a from-scratch port of each engine's line breaking, never shipped, kept as the plain-text correctness reference.
- Issue #321 is the public write-up of an offline study that emulated each engine's line layout (2026-09-15); entries cite its numbered decisions and side findings.

A size such as `633 cases; 124 / 73 / 128` counts the harness cases holding the shape at b1fd05fc, then those of them on Chrome's / Firefox's / webkit-host's accepted list. Dates say when a behavior was seen, and "by" a date means on or before it: in Chrome 153, Firefox 155 and Safari 26.5.2 until 2026-09-16, then Firefox 156.0 and Safari 27.0, then the pins of 2026-09-25 (`harness/pins.json`); a Safari sighting from before 2026-09-16 is unconfirmed on Safari 27 unless a webkit-host case holds it.

Before starting one:
- Rules whose errors cancel land together, in layers with a replay after each: #225's broader attempts lost old-suite cases that main then passed only because two of its errors, the U+3000 hang and controls before brackets, cancelled out (RESEARCH.md, Dead Ends).
- A prerequisite written here can be wrong: this file once said Firefox's breaks between styled pieces needed a model of its word segmentation, and turning on Chrome's joined-text rule for the Gecko profile sufficed.
- A fix may be on for one engine and off for another only when the off engine's losses come from a model named here as missing.

## Gaps

### Letter spacing

- Blink gives cursive-script runs no letter spacing except on spaces, Firefox none between joined Arabic letters, and Chrome none to U+202F (RESEARCH.md, Engine Facts); Pretext spaces every character. Real text shows it ("Arabic and Urdu with letter-spacing" on Chrome's and Firefox's lists): at 1.5px letter spacing in 16px Arial both paint `ابب` in `中（ابب）` 4.5px narrower than Pretext charges. Chrome before 149 lacks the rule or applies it differently, so a fix picks a version gate or a README line. #321's side finding 3 (by 2026-09-12).
- Characters with no advance take no gap in any engine, each by its own unit (in Blink per shaping cluster, in WebKit only on glyphs with an advance, in Firefox per cluster and none after a format character): with 1px letter spacing, two word joiners (WJ) at width 1px in 16px Arial are one line in all three browsers and split in Pretext (by 2026-09-12; attempts in RESEARCH.md, Dead Ends). A fix needs one per-grapheme spacing unit every rule shares, with per-segment arrays only where needed. Waiting on it: WebKit's return from a soft hyphen whose hyphen doesn't fit (`unfitHyphenRetreat`); a ZWSP right after a forced break inside a word, which all three browsers give a line of its own (it also waits on joined Arabic widths); Blink's shaping-cluster overflow units.
- Tab stops: the profiles' stops leave out the letter spacing Chrome's and Firefox's count; every tab gets its own gap, which Firefox gives only a tab ending its text run, as one before Arabic does; and Firefox's minimum of half a `0` is missing, while the WebKit profile's half a space (`tabStopAdvance / 16`) goes wrong once stops count spacing (RESEARCH.md, Engine Facts; 270 pre-wrap cases with a tab and letter spacing; 55 / 132 / 17). The errors can cancel, so some passes are luck: port the interval, the minimum and the gap in layers with a replay after each, and pin exact stop multiples in the unit test (43.6px isn't exact in binary). Blink's half-space skip is a separate gap. #321's side finding 2 (by 2026-09-12).

### Bidi levels, direction and script runs

Pretext takes no paragraph direction; only the Gecko scan resolves levels, taking every paragraph as left-to-right (RESEARCH.md, Bidi Levels; what that premise moved is under Break Opportunities From Engine Data). Without levels:
- WebKit keeps punctuation after an overflowing first character with it to the end of its item, which a level change ends, and the profile to the end of the scan's segment (`אב((tail` on a left-to-right page; 633 cases; 124 / 73 / 128, most under 24px). WebKit also asks its scan again where levels change (`ab””tail` in a right-to-left paragraph; 15 positions; 2026-09-23).
- Neutral characters measure in their neighbour's script: Chrome's `(` is 6.12px alone and 11px in an Arabic run. Safari paints a right-to-left `）` after Arabic at 9px, not 16px, so at 12-18px it keeps the U+202F after `中（ابب）` on that line, where Pretext gives it one of its own (67 cases; 14 / 13 / 4; by 2026-09-12). Chrome's page gives a run of neutral Latin-1 characters, such as `)` × 15 or `«»` × 8, the script before it, and its Canvas measures it as Latin, so in Amiri and Noto Naskh Arabic such a run after Arabic or Han paints wider than Pretext charges (RESEARCH.md, String Storage, 2026-09-27).
- Chrome measures under `<html dir>` as it was when the context was made, so text against the page's direction wraps slightly differently around brackets. A `direction` option fixed it in a prototype and wasn't taken (RESEARCH.md, Dead Ends); it's on the list for the API discussion planned for the end of the project (TODO.md; 2026-09-13).
- In a right-to-left paragraph Safari breaks `src/|עברית` and the WebKit scan doesn't; not a case (2026-09-14, Safari 26.5.2).
- Unwitnessed: whether `direction: rtl` alone turns on Firefox's document bidi, which decides where the Gecko scan must resolve levels.
- The Gecko scan doesn't split text runs where the script changes (RESEARCH.md, Decisions Log, 2026-09-24). Of the two fuzz strings in `harness/cases/followups.ndjson`, the `ko` one (Firefox 3 lines, the profile 4) is on Firefox's list; the `th` one passes in Firefox and is on Chrome's list for an untraced reason: Chrome keeps its final U+2007 on the last line, the library on a line of its own.

### Emergency breaks inside a word

- Each engine fits an overlong word its own way (#195): Chrome by right-context positions, Safari by line-start prefixes, Firefox by the advances of the word shaped whole. The Blink profile sums standalone graphemes: at 248px, `'ه'.repeat(140)` in `400 14px Helvetica, Arial, sans-serif` fits 62 isolated letters a line, Chrome 44 joined ones (2026-09-14). A mark that can't start a line sends the word before it through these fits (`foo@bar.com` before `，b`, where Pretext splits off `m`; 19 cases; 1 / 0 / 0). The WebKit profile fits past 96 graphemes from pairs (96 `ه` break where Safari does, 97 don't). The Gecko profile sums standalone graphemes in segments under 80px, a premise whose gap at 24-80px is measured in RESEARCH.md, Break Opportunities From Engine Data (RESEARCH.md, Decisions Log, 2026-09-27).
- Chrome keeps kerning across an overflowing word's break, which Canvas can't show (RESEARCH.md, Kerning At Line Edges), and Safari carries a broken word's remaining width to the next line unmeasured, which needs a Safari fit model that loses nothing (`'AV'.repeat(17)`: 3 lines, not 4, in 36 of 36 headless WebKit checks, 2026-09-15; RESEARCH.md, Safari (WebKit)). Neither is a case.
- In narrow boxes Safari keeps two joined Arabic graphemes on a line where Pretext splits them (by 2026-09-12, Safari 26.5.2).
- Splits inside a segment take Unicode graphemes; Firefox takes its own cluster starts, keeping a Myanmar spacing mark such as U+102C with the cluster before it, though its `Intl.Segmenter` splits them (by 2026-09-12, Firefox 155). Open: whether Firefox's other cluster starts beyond ICU4X's grapheme rules (a leading extender continues a cluster, a Bengali YA joins after a VIRAMA) undo the Gecko profile's use of Chrome's grapheme table (RESEARCH.md, Engine Facts, Firefox).
- Arabic joined across a soft hyphen is measured at isolated widths. For the Gecko profile, a ZWJ on each connected letter, gated by a check that a split's two sides add up, matched Firefox 155 on 1,458 of 1,576 Noto Naskh Arabic widths and can't reach Amiri or Noto Nastaliq Urdu (2026-09-12; RESEARCH.md, Content Language And Fonts). Prototype it with the Firefox halves of the rules that wait on joined Arabic widths, such as the ZWSP after a forced break under Letter spacing.

### Line edges: U+3000, soft hyphens and closing marks

- The Chromium and Gecko profiles hang a U+3000 run that ends a segment and miss four hangs: Chrome's in pre-wrap before a preserved space or tab (`中文`, U+3000, space, `中文` at 33px in 16px PingFang SC: 2 lines, Pretext 3) and at the next segment's start after a space, Firefox's after a word joiner (34 cases; 8 / 6 / 0), and Chrome's after an overflowing letter (2026-09-23). Firefox leaves a trailing U+3000 run out of the line's width even where it fits (2026-09-24).
- At a soft-hyphen break right after U+3000, Chrome paints no hyphen and Pretext adds `-` and overflows (`a`, U+3000, U+00AD, `b` in pre-wrap), and Chrome never lets a soft hyphen at a line start hold a line its hyphen doesn't fit (39 cases; 6 / 0 / 2; 2026-09-24).
- In real text WebKit, and sometimes Chrome, takes fewer soft-hyphen breaks than the library, moving the syllable before the hyphen to the next line (the accepted lists' "Real usage: soft hyphens", 2 / 0 / 15; the sample's soft-hyphenated draws are stand-ins, long words with a soft hyphen every few letters). Not traced; start from `bun harness explain sample-16a3704504259e8b --browser=webkit-host`, a Gatsby line at 352px.
- Chrome and Safari keep a soft hyphen at a paragraph or hard-break start, where Firefox and Pretext consume it. Still failing after #349, on the stand-in Canvas at b1fd05fc: soft hyphens ending the text after a line feed ("Soft hyphens alone after the last line feed", 8 / 0 / 5), a paragraph of only soft hyphens, and one starting a chunk before a word that doesn't fit. The likeliest fix is one line-start rule for soft hyphens and ZWSP (by 2026-09-12). Such a rule has two more facts to take (2026-09-27). Chrome and Safari keep a collapsible space that follows a soft hyphen where a line starts, and it takes room there: items `café`, ` \u00AD \u00AD`, `.`, `ab` in 16px Arial at 37.3px start their second line with the space after the first soft hyphen, 26.69px wide, in both, as their text in one node does in Chrome, where the plain-text walker consumes both (16 Chrome and 21 webkit-host cases of a 28,435-case rich probe, RESEARCH.md, Rich Inline Boundaries). And all three browsers keep a ZWSP where a line starts after a break at a space, after a soft hyphen too, so it holds a line where the word after it doesn't fit: `ab `, ZWSP, `xyzwxyz` and `ab `, U+00AD, ZWSP, `xyzwxyz` at 20px in 16px Arial take an empty second line in Chrome, Firefox and Safari, in one text node and as spans, where the plain-text walker consumes the ZWSP; rich inline keeps a ZWSP that starts an item.
- In Chrome, a soft hyphen right after collapsible white space ends no line where it starts past the line's width, since Blink finds the offset at the width before it, at the white space, and breaks there (`ShapingLineBreaker::ShapeLine`, `shaping_line_breaker.cc`); and where Blink breaks at white space right after a soft hyphen, the break takes that hyphen, since once the white space hangs, the break's offset follows a soft hyphen (`SetBreakOffset`). In 16px Arial `ab \u00ADcd ef` gives `ab` / `cd` with no hyphen at 20px, and `ab \u00AD cd` paints `ab -` at 41px. The Chromium profile takes neither rule: it ends the first line after the soft hyphen with the hyphen overflowing, which the harness's pass rule doesn't see for one text node, and ends the second at the white space without the hyphen. Where its hyphen doesn't fit a narrow line, Chrome also breaks inside the word, as for items `of`, `\u00ADfic`, `e` at 18px. Rich inline shows the first rule where the soft hyphen is in an item that continues a run from an earlier item: the line returns from the unfit hyphen to the break before the run, where Chrome ends it at the white space, as for items `–xyz漢a`, `b  \u00AD\u00ADab` at 67px: most of the 62 Chrome and 2 webkit-host cases of a 43,462-case rich probe that main passed and that hold a soft hyphen after white space inside an item. The first rule alone, in plain text and rich inline, fixed 98 Chrome cases of another probe and lost 32, which the second rule decides, so the two land together, as a plain-text change (2026-09-27, Chrome 154).
- Chromium keeps no-break characters on a soft hyphen's line, where WebKit breaks before them; trace Blink first (by 2026-09-12).
- At a chosen soft hyphen Chromium paints U+2010 where the primary font maps it and Pretext measures `-` (widths move 4.4-6.5px in Geeza Pro, which doesn't map it); Firefox's hyphen line is one letter-spacing gap narrower. RESEARCH.md, Measurement Model, has how Canvas can tell a font's own hyphen. #321's side finding 9 (by 2026-09-12).
- Chrome's `text-spacing-trim` (`src/han-kerning.ts`) isn't modeled inside a unit that takes emergency breaks: Chrome fits `」。b` at 33px in 16px Arial, where Pretext charges 32px for `」。` (2026-09-14), and lays out `『是的。』` before a line feed in pre-wrap 16px PingFang SC in 4 lines at 16-31px, Pretext 5; widths miss even where lines match (`中」`, U+00AD, `中` at 24-32px: 24px in Chrome, 41.68px in Pretext; 2026-09-27). Pretext's port takes two premises: each character of a pair takes the font Canvas draws it in, where Blink types both by the font of the one it halts (trims to half width) (no line changed in 5,736 Chinese and Japanese corpus cases, Chrome 153, 2026-09-23), and nothing halts across rich-inline items.

### Negative letter spacing and hanging spaces

Main before #340 matched most of these only while it started the next line with the space.
- At −6 in pre-wrap the browsers don't fit a word after a hanging space, and Pretext does (` A B` in 16px Arial; 7 cases; 3 / 0 / 1; 2026-09-15).
- Chrome ends a line before a space after a soft hyphen, where Pretext hangs the space (`a`, U+00AD, space, `b`; 161 cases; 50 / 2 / 25; 2026-09-15).
- At −1 in pre-wrap, Safari and Firefox give the space after `لا` in `a لا ب` (1px, 32px Arial) a line of its own, where Pretext hangs it (2026-09-15, Safari 26.5.2).
- In pre-wrap Chrome hangs preserved spaces and tabs after an overflowing letter, where Pretext starts the next line with them (by 2026-09-12).
- Pretext disagrees with itself: text laid out again at its widest line can break earlier, since a space, a ZWSP and a soft hyphen fit before the negative gap the reported width includes (Gecko profile, stand-in Canvas: `x.ywordy\t\t foo` in pre-wrap at −1 is 83.48px wide at 99px, and at 83.48px its second tab moves down; 2026-09-15, rechecked at b1fd05fc). Shrink-wrap callers such as the bubbles demo meet this.

### White space and controls

- The scans read Pretext's collapsed white space, not each engine's (Blink keeps FF as text in normal white space, WebKit CR and FF in both modes); the Gecko scan reads the source's, so its breaks follow Firefox but its widths come from the collapsed text (2026-09-23).
- Lone CR, FF and VT in pre-wrap: Pretext takes CR and FF as hard breaks and VT as text, and each engine differs (in Firefox `ab cd`, CR, U+00AD, CR, `ef gh` takes a line too many at 12-48px; the accepted lists' "Pasted C0 and C1 controls"; the README tells apps to normalize `\r`). Two per-engine CR prototypes each lost results main before #340 got right (RESEARCH.md, Dead Ends): trace the engines' line builders first (by 2026-09-12).
- Before encoding any rule for controls, trace Firefox's line-end hang and trim rules for spaces, CR, FF and tabs. It moves a pre-wrap tab that doesn't fit to the next line, back to the last break (under `break-word`, to just before the tab), where the Gecko profile, which already doesn't hang it (`hangTabs`), ends the line after it (`https://ex.com\tfoo` at 101px in 16px Arial: Firefox `https:// | ex.com\tfoo`, Pretext `https://ex.com\t | foo`; 77 cases; 3 / 7 / 0; 2026-09-14). It trims U+1680 at line edges (40 cases; 0 / 2 / 0), fits negative letter spacing before preserved spaces otherwise (13 cases; 1 / 1 / 1), and makes a hidden control a cluster a line must hold (`a`, NUL, `ff` in 24px Amiri; 16 cases; 1 / 11 / 0) (by 2026-09-12).
- Firefox removes a newline between wide characters and, for `ja` and `zh` content, next to East Asian punctuation; content without a language takes the second rule from the OS regional locale, which a page can't read, so there the Gecko profile removes only the first kind (by 2026-09-12).
- Firefox leaves soft hyphens and bidi controls (LRM, RLM, ALM, U+202A-U+202E and U+2066-U+2069) out of its text runs, and since #368 the Gecko profile's analysis gives a run of them to the segment before it (RESEARCH.md, Break Opportunities From Engine Data).   - After NEL or another C0 or C1 control, which stays a segment of its own, a run of controls is a text segment of its own, and the break Firefox takes after the NEL isn't one where a ZWSP follows the run: NEL, PDI, PDF, ZWSP, U+0651, soft hyphen, `a`, LRI, `ab`, space, soft hyphen, `a` in 16px Arial takes 6 lines at 1-4px in Firefox and 5 in Pretext (4 cases, failing before too).
  - An ideographic space that ends a word hangs only where a line takes the word whole, not where it fills the word's graphemes: LRE, `bש`, PDI, U+3000, tab takes 2 lines at 12px in Firefox and 3 in Pretext (5 cases, failing before too).
  - Firefox keeps a space before a control and a combining mark as the mark's base (`IsSpaceCombiningSequenceTail`, `nsTextFrameUtils.cpp:24-30`): NEL, U+0651, `「`, tab, ALM, tab, U+0651 takes 2 lines at 24px in Firefox and 1 in Pretext (1 case, which passed before).

A run that starts a paragraph or chunk is text of no width to the walkers, so a space after it takes letter spacing as after a character: LRM, space, `ab cd` at letter spacing 5 fails at 38-42px and 74-78px, and `ab`, LF, LRM, space, `cd ef` in pre-wrap at 9-13px, 37-41px and 70-74px (25 cases, failing before too).

  - Not traced: `ab`, ZWSP, LRM, `cd ef` at 1-8px (8 cases, which passed before), and RLM, space, PDF, RLM, soft hyphen and two spaces in pre-wrap at letter spacing 2 at 6px (failing before too).

### Rich-inline item edges

Since #369 (2026-09-27) an item's walk continues the line (RESEARCH.md, Rich Inline Boundaries, Continuing The Line), which fixed the soft-hyphen and U+2028 shapes this list held before: a soft hyphen that starts an item after other content is a break, an item of only a soft hyphen keeps the collapsed space before it, and an item holding a U+2028 or U+2029 that the WebKit scan makes a hard break ends its line there. What's left comes mostly from items measured apart, from white space beside soft hyphens and bidi controls at an item's edge, and from spans that browsers lay out otherwise than their text in one node. Counts from 2026-09-27 and 28 are of probes (RESEARCH.md, Rich Inline Boundaries) in Chrome 154, Firefox 156.0.1 and webkit-host.

Measured apart:
- Chrome and Firefox shape and kern across same-font items and Safari doesn't kern there, so item widths miss by about 1px at a boundary, more where one splits a cluster (RESEARCH.md, Rich Inline Boundaries, Joined Text). All three join Arabic letters across items, which items measure apart: in 16px Arial items `A`, `V`, `A` are 29.64px wide in Chrome and Firefox and 32.02px in Safari, as Pretext measures them, and items `\u0628`, `\u0628`, `\u0628` are 19.23px in all three, where Pretext charges 34.24px, so items `\u200B\n\u200B \u0628\u0628`, ` \u00AD`, `\u0628`, `\u0628` at 50px take 2 lines where Safari lays out 1 (2 of the 4 webkit-host cases of a 32,830-case probe that lose against main as spans only). Firefox, which drops soft hyphens from its text, also forms an emoji ZWJ sequence across one that starts the next item: items `a👩\u200D`, `\u00AD🚀b` in 12px Arial at 20px take 2 lines in Firefox, the first ending with one astronaut glyph, and 3 in rich inline (1 Firefox case of the 28,435-case probe that main passed). A prepare-time boundary correction for Blink and Gecko was deferred on 2026-09-26, since rich inline with kerning between sibling spans is a large project (RESEARCH.md, The Per-Engine Rebuild And What Counts As Done).
- A soft hyphen that starts an item has no text before it to measure joined with the text after it, as the plain text measures how much narrower Arabic letters join across a soft hyphen, so the line returns from that hyphen where it overflows by less than the joining saves: items `بب ببب`, `\u00AD\u0650ببب بب` in 24px Noto Naskh Arabic at 66px give 3 lines where Firefox and the plain text give 2, and 3 more such probe cases at 66-82px in Noto Naskh Arabic and Arial. Measuring the two items' texts joined would add Canvas calls.
- A rich item that continues a run from the item before and starts with characters that the joined text keeps with that item's end, as U+202C after `。`, is one segment in its own text, where the joined text breaks after those characters. Where that segment has fresh-line geometry (`src/entry-geometry.ts`), as for a default-ignorable code point in desktop Chrome and Firefox, a line doesn't end inside it (`recordJoinedBreaks()`), so it returns to the break before the run: items `x `, `。`, `\u202C\u0628\u0628` take 3 lines at 20px on the stand-in Canvas where their text in one node takes 2, on main before #369 as well. The same holds in Chrome after an item of only a soft hyphen whose next item starts with a bidi control that the joined text breaks after: items `see`, U+00AD, `\u2066this word` in 16px Arial at 34.6-50.7px break `this` between letters, and `word `, U+00AD, `\u200Fmore text` at 44.4-75.6px end the first line at the space before the soft hyphen, where Chrome, as for their text in one node, breaks after the control (10 Chrome cases of the rich set; main before #373 failed them too).

### Fitting arithmetic

Each engine's line fit is exact in its own units (RESEARCH.md, Measurement Model); the Blink and Gecko profiles fit with a 0.005px allowance instead, a named gap, not a tolerance to tune. Its cost sits under the "Within 1/64 px of where the browser's lines change" headings, most on Chrome's list; Chrome's real-usage Japanese and Chinese lines, which fit one more character than the Canvas widths add up to, may be the same (untraced).
